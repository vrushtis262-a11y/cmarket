Performance Architecture
------------------------
The final performance state reflects several cumulative changes.

1. Indexed Order Lookup

OrderManager maintains an unordered index from OrderId to active-order
storage position.

This removes repeated linear scans for operations such as cancellation,
modification, and direct OrderId lookup.

2. Price-Time Priority Indexes

OrderManager maintains separate ordered priority indexes for buy and
sell orders.

Buy priority is ordered by:
- Higher price first
- Lower sequence number first
- Lower OrderId as a deterministic tie-breaker

Sell priority is ordered by:
- Lower price first
- Lower sequence number first
- Lower OrderId as a deterministic tie-breaker

These indexes allow the matching engine to locate the highest-priority
resting order without scanning every active order.

3. Observable Active-Order Storage

The active-order vector remains the authoritative storage container.

Cancellation retains swap-with-back behavior.

FIFO execution priority does not depend on physical vector position.
It is determined by price and sequence number through the priority
indexes.

4. Transactional Mutation Journals

Hot matching paths avoid copying the complete OrderManager for
rollback.

Instead, operations record targeted mutations and restore them in
reverse order if an operation fails.

This approach is used by:
- Active-order market execution
- Crossing limit-order placement
- Price-changing modification

5. Transactional Order Removal

OrderManager supports extracting an order together with the index
state required to restore it.

This allows filled or temporarily removed orders to be restored without
rebuilding the complete active-order manager.

6. Same-Price Modification Fast Path

Same-price modifications avoid rebuilding or copying full matching
state.

A quantity decrease preserves FIFO priority.

A quantity increase receives a new sequence number and therefore loses
its previous FIFO priority.

7. Lightweight Trade Rollback

TradeStore uses checkpoints so failed matching operations can restore
trade-history state without copying the entire trade vector.

8. OrderBook Synchronization

OrderBook uses shared/exclusive synchronization.

Read-only access uses shared locking while mutating operations use
exclusive locking.

Explicit copy operations preserve the snapshot behavior required by
remaining rollback paths.

Complexity Notes
----------------
The indexed architecture changes the dominant lookup behavior of
several operations.

OrderId lookup:
Expected O(1) through the unordered index.

Best resting order lookup:
O(1) access to the beginning of the corresponding ordered priority
index after index maintenance.

Priority-index insertion/removal:
O(log n).

Active-order cancellation:
Expected O(1) vector/index lookup work plus O(log n) priority-index
maintenance.

Matching:
No full active-order scan is required to discover each next resting
match. Each matched order still requires the corresponding state,
priority-index, order-book, and trade updates.

Benchmark Interpretation
------------------------
These measurements should be interpreted as comparative engineering
results rather than hard real-time guarantees.

The benchmarks run on macOS on a general-purpose Apple M1 system.
Scheduler activity, CPU frequency behavior, thermal conditions,
background processes, compiler version, build flags, and machine
configuration can affect observed values.

Worst observed latency is especially sensitive to operating-system
noise. p50, p95, and p99 are therefore more useful for comparing
implementation changes.

The largest speedups also compare implementations with different
algorithmic behavior. They demonstrate removal of previously measured
hotspots rather than guaranteeing the same multiplier for arbitrary
production workloads.
