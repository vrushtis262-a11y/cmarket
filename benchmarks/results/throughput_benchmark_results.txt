cmarket Throughput Benchmark Results
====================================

Overview
--------

This benchmark measures sustained matching-engine throughput across
several representative workloads.

The goal is to measure how many operations the engine can complete per
second after the accepted performance optimizations.

The benchmark includes:

- pure limit-order placement
- heavy matching
- place/cancel activity
- place/modify activity
- a mixed steady-state workload


Benchmark Configuration
=======================

Operations per workload:

100,000

Initial active orders for populated-book workloads:

100,000

Measured metric:

Throughput = completed operations / elapsed time

Workload Definitions
====================

Order Placement
---------------

Measures non-crossing limit-buy placement.

The workload begins with an empty matching engine and places:

100,000 limit-buy orders

at a common non-crossing price.


Heavy Matching
--------------

The engine is first populated with:

100,000 resting buy orders

The measured workload then submits:

100,000 crossing limit-sell orders

Each incoming sell order can execute against resting liquidity.


Place/Cancel Mix
----------------

The engine begins with:

100,000 active buy orders

The measured workload alternates between:

- placing a new limit-buy order
- cancelling an active order near the middle of the order collection

Each placement and cancellation counts as one operation.

The total measured operation count is:

100,000


Place/Modify Mix
----------------

The engine begins with:

100,000 active buy orders

The measured workload alternates between:

- placing a new limit-buy order
- modifying an active order near the middle of the order collection

Each placement and modification counts as one operation.

The total measured operation count is:

100,000


Mixed Workload
==============

The mixed workload begins with:

100,000 active buy orders

Each 10-operation cycle performs:

4 limit-order placements
2 cancellations
2 modifications
2 crossing limit-order submissions

This produces the following workload distribution:

40% placement
20% cancellation
20% modification
20% matching

The total measured operation count is:

100,000

Measured throughput:

6,019 operations per second

Profiling Findings
==================

A 20-second macOS sample was collected during a throughput benchmark
execution.

Because the complete benchmark takes substantially longer than the
sampling interval, this profile represents a window of the benchmark
rather than an equal sample of every workload.

The sample identified significant execution time in:

MatchingEngine::place_limit_order()

and:

OrderManager::cancel_order()


A substantial portion of these paths was associated with:

_platform_memmove


This is consistent with the current active-order representation.

OrderManager stores active orders in a contiguous vector.

Operations that erase orders can therefore require movement of
subsequent elements.

The profile also showed memory-allocation activity during order
placement, although vector movement was substantially more prominent
in the sampled execution window.


Remaining Performance Constraints
=================================

Order Placement
---------------

Non-crossing order placement is now the highest-throughput core
operation measured by the benchmark.

Throughput:

41,046 ops/s

Earlier architectural changes removed full aggregate order-book
reconstruction from this common path.

Remaining scaling cost is influenced by growth and management of the
active-order collection.


Matching
--------

Heavy matching achieved:

4,358 ops/s

The matching engine still searches active resting orders to identify
the appropriate execution candidate.

This remains an important scaling constraint at large active-order
counts.


Cancellation
------------

The place/cancel workload achieved:

9,366 ops/s

Profiling shows that cancellation remains strongly affected by vector
erasure and memory movement.

This agrees with the latency benchmark, where cancellation showed the
largest relative latency growth as book size increased.


Modification
------------

The place/modify workload achieved:

4,968 ops/s

Modification performs more work than direct cancellation because it
must preserve matching-engine semantics while updating the order.

Its cost includes maintaining:

- price-time priority
- aggregate order-book consistency
- order state
- exception-safety behavior


Mixed Workload
--------------

The mixed workload achieved:

6,019 ops/s

This benchmark combines placement, cancellation, modification, and
matching against an engine initialized with 100,000 active orders.

It provides the most representative single throughput number in the
current benchmark suite.


Optimization Decision
=====================

The final profiling pass did not identify a small isolated hotspot
whose removal would justify another localized optimization.

The major remaining costs are tied to data-structure choices:

- contiguous active-order storage
- vector erasure and resulting memory movement
- linear active-order search during matching
- modification work required to preserve engine invariants

Improving these areas would require a larger architectural change,
such as introducing price-level-aware queues or an indexed active-order
representation.

A previous hash-based OrderId index was experimentally evaluated and
rejected because its measured end-to-end improvement was only
approximately:

0.71%

The remaining performance work should therefore be treated as future
architecture design rather than additional micro-optimization.
